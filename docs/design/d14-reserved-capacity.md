# D14 bounded-capacity deployment design

**Status:** thesis-completion scope, 2026-10-15. This is a bounded design and open-obligation record, not implementation or qualification evidence. The detailed global-ticket proposal is retained historically at commit `9fb5dd6` (`docs/design/d14-reserved-capacity.md`); this file replaces that proposed mechanism.

## Adopted obligation and claim boundary

D14 retains SQLite WAL with `synchronous=FULL`, preallocated or reserved audit capacity, fault injection for write/fsync/disk-full/corruption, recorded filesystem assumptions, and restart-persistent `UNKNOWN`/`INVALID` outcomes (separate `MSE_MA_Thesis` repository: `tbound/AH-technical/10-decision-register.md`, D14, and `tbound/AH-technical/02-1-recovery-and-continuation.md`). Storage must cover protected journal/WAL and emergency records, and first-write ENOSPC/EDQUOT must be tested.

This finish model covers one local claim-bearing service behind the CLI, one active workflow, and serialized effects. Remote/multi-user operation and malicious host administrator, kernel, or hypervisor behavior remain outside the thesis boundary. The service must not share its protected allocation budget with task output/workspace writes. If the thesis retains a claim against non-cooperating privileged host writers, this bounded model is insufficient and requires an explicit scope decision before implementation.

## Bounded deployment model

- Put audit, owner, and protected-root state on a dedicated service-owned filesystem or a strict service quota. A `StateDirectory` on an ordinary root filesystem alone does not reserve capacity. Bind and verify the deployed mount/quota identity and filesystem behavior at startup; ensure host backing storage cannot run out before the guest reserve is usable.
- Physically allocate a fixed reserve before each governed effect. The bound must include the maximum terminal audit outcome, owner checkpoint/proof transaction and WAL, protected-root terminal anchor and WAL, plus filesystem allocation/journal overhead. Include the pre-effect intent path in the capacity analysis. Derive the size from enforced serialized limits, SQLite page/schema behavior, and the selected filesystem; do not use the prior 64 MiB experiment size as a production bound.
- Keep a durable unresolved-workflow admission rule. At startup and before any new request ID, independently reconcile prior requests. A missing terminal record or any `unknown` terminal response remains unresolved and blocks new workflow IDs. Allow only exact-ID recovery under D20's original authority and budget rules; never replay a consumed effect or treat transport completion as proof of settlement.
- Reuse the existing authenticated local service request/effect records and cross-process singleton lock if they prove these properties end to end. Do not add a `ProtectedTrustedRoot` global ticket, new schema, generalized private capacity profile, or all-system writer mutex unless a failing test shows the bounded service model can be bypassed or the reserve lifecycle cannot be recovered from existing records.

## Required terminal-settlement evidence

Before admitting a new workflow, fresh-process verification must bind the same effect identity across: (1) the durable audit intent and known terminal outcome; (2) the owner terminal checkpoint, event, and proof; (3) the protected-root head anchoring that owner state; and (4) independent evidence for the controlled effect and its completion or absence. `UNKNOWN`, missing records, mismatched identities, and unverified reserve state block admission. They are not successful completion.

Use a physically full protected filesystem or quota to induce real ENOSPC after a controlled effect. Decision 3 (2026-10-15): release and sync the reserve before the protected terminal writes that need its space, then prove the maximum-bound audit, owner, and root terminal writes complete. The reserve must not be held through terminal accounting: allocated space is not usable while allocated, so a release after terminal durability cannot satisfy ENOSPC. That ordering (R1 "P2") is superseded by Decision 3 of this document. The R1 evidence keeps its original wording. Inject crashes before and after reserve release and at terminal-write boundaries. A crash after release stays unresolved and blocks new IDs until a fresh process reconciles durable intent and reserve markers; the reserve is never replayed. A fresh process must either verify all linked terminal records and permit settlement, or retain the unresolved workflow and refuse new IDs. Failure to allocate the reserve must refuse before callback entry. Keep syscall EIO, corruption, and declared-platform power-loss assumptions as separately stated fault cases; a successful `fsync` return alone is not power-loss evidence.

## Existing partial evidence and open obligations

The ext4 experiment receipt at [reserved-capacity-ext4-experiment-20261014.json](../evidence/reserved-capacity-ext4-experiment-20261014.json) records real guest-filesystem ENOSPC, reserve release, audit/owner/root terminal writes, and fresh-process refusal after a crash following release. Its small synthetic checkpoint does not exercise maximum enforced checkpoint/proof sizes, qualify the production volume or host backing storage, or prove global unresolved-request admission. It is feasibility evidence only; it does not complete D14.

Logical owner headroom (2026-10-15) is enforced for `ReserveEffect`. Before grant, the owner's write transaction reads its connection's `max_page_count`, `page_count`, and `freelist_count`, and refuses with the existing `ErrExhausted` unless the free pages plus unused ceiling headroom hold the reservation's encoded rows plus the worst-case terminal transition: three maximum-size (16 MiB) blobs, where the state rewrite carries one and the event record carries checkpoint and proof, 13443 pages with B-tree slack (`sqliteTransitionPages`, `requireEffectTerminalHeadroom`). The derivation takes a usable page of at least 3841 bytes, since the header's reserved-byte count is at most 255. That gives 3837 payload bytes per overflow page and at least 457 bytes per record kept on its leaf page. Row overhead is at most 1024 bytes (the state row at most 599, an event row at most 418). Assumption A5, argued from the SQL shape and not traced in bytecode, is that each of the four B-trees a transition touches takes one balance chain. The pinned SQLite 3.53.4 (modernc.org/sqlite v1.60.1) caps a cursor at 20 levels, so under A5 each chain adds at most 4 pages per level plus 1 for a root split, and the slack is 4*(4*20+1) = 324 pages. A real-SQLite probe measures 12300 pages for one maximum-size transition. The default-on gate tests refuse each probed ceiling below the threshold before any grant, and they grant and settle the threshold ceiling for the 23-page fixture terminal only; no worst-case terminal is probed, and no ceiling above the threshold is probed. The bound covers the reservation's rows and its terminal rows only.

While an effect is reserved, the other commits of the same workflow are refused before any write, each with its typed error. `AdvanceCheckpoint` (including the capture and result checkpoints), `ReservePreEffectRetry`, `ReserveHostCall`, and a second `ReserveEffect` return `ErrPendingUnknown`. A clean restart cannot be built, because `ObserveRecovery` refuses an observation that holds a reserved effect with `ErrPendingUnknown`. Fresh initialization of an existing workflow ID returns `ErrCAS`. `TestD14ReservedEffectRefusesNonTerminalCommits` pins these refusals and the head each one leaves unchanged. Outside tests, the ledger is the only caller of the owner's compare-and-swap. A direct call with a forged, untyped proof is refused with `ErrObservation` (`TestReserveEffectUsesTypedNoTokenReservation`). So the only owner commit the ledger admits between a grant and its terminal is that terminal.

Residual risks that the owner gate does not close: (1) the protected-root terminal anchor is not headroom-gated, so a root failure after the owner terminal commit poisons the owner (fail-closed, with the effect unresolved); (2) another workflow that shares the owner file can consume the reserved headroom, and the owner does not refuse it, although the production catalog maps one owner file to each workflow ID. The protected root (4096-page ceiling) is otherwise not bounded, and its fence, epoch, and clock writes are not gated either. WAL and host storage are not bounded, and nothing here qualifies physical D14.

Open work is limited to: establish the dedicated filesystem/quota and backing-space assumption; derive and enforce a physical reserve bound for the protected volume, which the owner gate above does not provide; verify the authenticated service singleton; add or prove the durable unresolved-request admission rule, including `unknown` terminal responses; exercise maximum-bound terminalization and crash points through the retained production path; and preserve fresh-process receipts. Expand to a global ticket only if one of these tests demonstrates the simpler model is inadequate.
