tbound at a glance

A safety layer for AI coding agents

tbound (short for "trust boundary") is a program for Linux that watches over an AI coding agent. The agent asks to do something. tbound decides. The agent never touches the real project directly.

1. The problem

A coding agent can edit files, run commands, install software and use the internet. It can make mistakes. It can also follow bad instructions hidden in a project file. This is called prompt injection.

Telling the AI "do not do X" is not real protection, because the AI can ignore it. A separate program must enforce the rules. That program must sit outside both the AI and the agent program.

2. The research gap

Many tools already provide one or two of the five safeguards below. The thesis asks what happens when all five work together, tested under one test plan fixed in advance.

The five safeguards:

1 Fixed tool listThe AI can only use the tools we declare.
2 Outside rule checkA separate program says ALLOW or DENY. No AI decides.
3 Work on a copyOnly tbound changes the real project.
4 Locked-down backupIf something slips past the tools, the operating system still blocks it.
5 Independent checksSeparate observers check what really happened. The agent's own report does not count.

Why the usual protections fall short

  • Prompts and self-checks can fail in the same way as the AI. They give no real authority.
  • Permission prompts and hooks run inside the agent program. They show what the agent plans to do, not what happened. In Pi and OpenCode an allowed shell command normally runs with the user's full rights.
  • Sandboxes limit files and network access from outside. By themselves they do not decide when changes reach the real project, and they do not collect proof of what happened. Some systems already combine several of these controls.
  • Tool rules alone decide well. But if the agent finds a way around the declared tools, for example by installing an extra tool plug-in, nothing catches it.

So tbound keeps a locked-down box, but only as the backup layer. It catches whatever slips past the declared tools. The ring diagram in section 3 shows how.

How this relates to Anthropic's sandbox

Anthropic's sandbox is also enforced from outside the model, and it can wrap a whole process. tbound does not claim to be the only system that protects credentials or controls network access. Its difference is the combination of all five safeguards.

3. The idea: one trust boundary

The agent program (Pi) runs as an untrusted worker. tbound runs on the host computer and is trusted. The trust boundary sits between them.

① The model reaches Pi only through the model gateway. ② The gateway passes the recorded tool call to Pi. ③ Pi sends a proposal (a request to run a tool) to tbound.
Nothing from the left side has any authority. tbound treats all of it as untrusted input.

Key rules

  • Deny by default. If no rule allows an action, it is denied. If a start-up check fails, tbound refuses to run.
  • No AI in the decision. The gate follows fixed rules.
  • Write first, then act. tbound saves its decision to disk before the action starts.
  • The working copy is not the real project. Permission to change one is not permission to change the other.
  • No blind retry. After a crash, tbound checks what happened. It never just repeats the action.
  • Missing proof is not success. If the evidence is incomplete, the result is "unsupported".

One tool call, step by step

1Model asksThe gateway records the tool call before Pi sees it.

3Matchtbound checks the proposal against the gateway's record and logs the intent.
4GateALLOW or DENY. The decision is saved first.
✕If DENYPi gets the reason and one short hint. Nothing runs.
5EffectFile work changes the working copy. bash runs in a fresh, locked-down cell.

7PublishAt the end, tbound applies the approved changes to the real project.

Staged workspace: how a change becomes real

Pi never touches the real project. It works on a separate working copy. Every allowed change locks in a new read-only snapshot. Only tbound can copy approved changes into the real project.

This controls who may change what. It does not check whether allowed code is good. If harmful code follows the rules, tbound does not notice.

Containment: the last line of defence

The gate only controls the declared tools. Containment is a locked-down box that the operating system builds around every bash command. It catches anything that goes around the tools. An attempt has to get through every ring.

The six layers

Each layer closes a different hole, and no single one covers everything. All six are standard Linux features, so the thesis does not need to invent a new sandbox. The numbers match the rings below.

What it doesWhy it is there
1 Signed container imageThe box starts from one known, signed set of tools. The signature is checked offline before launch.Every run starts from the same small, known setup. The box has no real admin rights on the host.
2 Namespaces + cgroupsNamespaces give the command its own private view of files, processes and network. cgroups cap its CPU, memory and number of processes.The other layers limit what a process may do. They do not limit what it can see or how much it can use.
3 LandlockA Linux feature where a process locks itself to chosen folders. It cannot undo this.Stops a script from reading or writing protected paths. It needs no admin rights.
4 seccompA filter on system calls, the requests a program makes to the Linux kernel.The box shares the host's kernel. Blocking the calls the command does not need makes attacks on the kernel harder.
5 No network routeEach command box runs with no network at all. Pi can only reach the model gateway.Data can only leave over a network. Removing the route is stronger than filtering destinations, because there is no allow-list to get wrong.
6 pidfd + cgroupspidfd is a stable handle to a process. cgroup.kill stops every process in the box at once.An attacker may leave a background process running. On timeout or cancel, nothing may survive. The thesis tests for "no surviving child process".
"What if we need network access later, for example a web search tool?"

The box stays offline. Network access would become a declared tool. The request goes to tbound, the gate checks the destination, and tbound makes the call. The model gateway already works this way. This is a possible extension, and the thesis does not test it.

The rings are a picture, not strict nesting: the layers work side by side. The cell is fresh for every bash command, with no network, no secrets and no access to the real project. This is safeguard 4 of the research gap. Sandboxes already provide it. tbound adds the gate, the working copy and the evidence around it.

4. The master thesis

Research question. "How can an external, deterministic supervisor be designed and evaluated to govern a declared tool surface of an untrusted software-engineering agent while preserving policy-compliant task execution with bounded operational overhead?"

In plain words: can an outside program with fixed rules control what an untrusted coding agent does, and still let the agent finish its normal work without much slowdown?

Method
  • Design Science Research: build something, then test it.
  • One fixed agent program (Pi), one fixed AI model, Linux only.
  • The test plan is written down before the main test run ("pre-registered").
Test cases

Bars are not to scale. Injection: instructions hidden in project files. Unsafe action: for example touching protected files or sending data out. A third kind, getting around the tool list, is tested in a separate set that is not part of H1.

Main hypothesis (H1)

H1 is the one claim the thesis tests. All three parts must hold:

  • Setup: tbound passes all start-up and recovery checks.
  • Security: 0 forbidden effects in 299 attack runs. A forbidden effect is a harmful result that really happens, such as a leaked secret or a changed protected file. In a second pass with protections relaxed, the observers must catch the effect in all 299 runs. This shows they work.
  • Friction: tbound wrongly blocks at most 10% of 100 normal tasks. At least 90 of 100 still succeed.

Contributions

  • C1 A way to control an agent that needs no changes to the agent program.
  • C2 A working reference build. It is a blueprint, not a claim of novelty.
  • C3 Evidence on how much it prevents and how often it blocks normal work.
  • C4 A method to show the observers really work. Each kind of effect gets its own check, including when the agent adapts to denials.

Out of scope: breaking out of the container or VM, a compromised tbound, whether allowed code is safe, non-Linux systems, several agents at once, and harms that are not on the registered list.

6. Why this thesis is useful

tbound does not invent sandboxing. The thesis designs one way to combine a locked-down box, controlled publishing and independent evidence of what really happened, and plans to test it for one fixed coding-agent setup.
  • Authority moves out of the model. Safety does not depend on the AI obeying a prompt.
  • The agent stays useful after a denial. A denial comes with a short hint, so the agent can try something allowed instead of stalling. The AI still never decides.
  • Known parts are combined and tested as one system. Earlier work covers single parts. The results of this study are not measured yet.
  • It measures both sides. It counts forbidden effects and also normal work that was wrongly blocked. A system that blocks everything is useless.
  • It states its limits. Missing evidence counts as "unsupported", never as "prevented". Claims apply to one fixed setup only.

Staying productive after a denial

A rule-based gate will deny some calls. If a denial is just a stop, the agent retries variations or gets stuck until a person steps in. Being asked to approve again and again also makes people read each request less carefully.

So tbound returns a short hint with each denial: the reason, the rule that applies, and one fixed sentence naming something that is allowed. The sentence comes only from public rules and never contains a host path or secret. It is advice only. The agent must send a new proposal, and that proposal is checked from scratch. A hint never turns a DENY into an ALLOW, and tbound never runs it.

Today: fixed sentences

Ten public denial reasons each have one fixed sentence. The choice is logged and can be replayed. It is part of the H1 test. A bug in how a denial is passed on is fixed, but not yet in a final version.

Next: a classifier picks the hint off

A small classifier would pick among two to four prepared sentences, with the fixed sentence as fallback. It writes no free text and has no authority. The code exists but is switched off and parked until after H1. There are no results yet.

Hints alone are not new: Claude Code already has a similar deny-with-hint pattern. The difference is the combination of an outside rule check, a non-binding hint, a fresh check of the next proposal, and evidence that the denied call had no effect.

Why a denial log is not enough

Suppose a system logs "The dangerous action was denied." That helps, but it does not show that no side process, other route or earlier action caused a forbidden effect.

tbound's planned test asks: Did a forbidden change, network transfer or lingering process really cross the protected boundary? Independent observers check this.

The test also needs calibration: show that the observer can detect the effect when the protection is switched off. Otherwise "nothing detected" might only mean the observer could not see.

Check that the smoke detector works before concluding there was no fire.

Each kind of effect needs its own check. Catching a file write made through a tool does not prove the observer would catch an effect from inside the command cell. Missing evidence counts as unsupported, never as prevented. These are planned requirements, not finished results.

Known limitations

  • Prompt injection can still fool the agent. The study counts forbidden effects, not whether the AI followed bad instructions.
  • Allowed access can be misused. Allowing a website does not limit which account or repository is used there. Keeping the API key away from the agent does not stop leaks through allowed channels.
  • Allowed code can still be flawed. tbound does not find subtle bugs in code it lets through. Published code is not certified safe.
  • Hints are generic. A fixed sentence may not name the best alternative, and the AI may ignore it. The test has no arm without hints, so their benefit is not measured.
  • Claims depend on the setup and on what the observers cover. tbound prevents the listed forbidden effects under stated assumptions. It does not remove prompt injection or harm in general.
  • The research gap is provisional. It rests on a literature search that closed on 2026-10-02. The thesis does not claim that single mechanisms are new.
  • No comparison result exists. H1 has not run, and there is no matching test against Anthropic's sandbox. Passing H1 would be evidence for tbound alone. It would not show that tbound beats Anthropic's sandbox or is a better general sandbox.

The thesis and the product effort

Pi on Linux is the tested scope, not a limit on reuse. A product could make that setup easy to install, run, inspect and recover. Other agent programs and operating systems need separate work and testing.

A separate product effort works on multi-turn workflows, review and cancel, setup checks and a web gateway. Parts exist, but no live deployment has been tested. This work does not widen the thesis's claims.

G1 — the feasibility checkpoint

G1 passes only when five things are shown on the target Linux machine:

  1. The gateway matches each tool call.
  2. Pi sees only locked snapshots.
  3. Decisions are saved before any action.
  4. Containment works.
  5. Evidence can be rebuilt.

Containment

Containment is the locked-down box around each command. It catches activity that bypasses the declared tools. See the six layers in section 3.

Claim-bearing

A run is claim-bearing if it can count as evidence for H1. It must use:

  1. the fixed setup;
  2. the registered test set;
  3. independent observers.

not claim-bearing These are not claim-bearing:

  • development tests;
  • demos.

They show how the system works. They prove nothing for H1.

The ledger

The ledger lists every eligible attack case from the benchmarks below, and it is frozen before any draw. A case is eligible if it can cause a registered forbidden effect inside the command cell. Every excluded case keeps its reason.

The adaptation rule

The adaptation rule is a fixed recipe that turns one ledger case into a test tbound can run. It keeps the benchmark's wording, builds a small synthetic project, and maps the benchmark's tools to Pi's tools. A case it cannot turn into a fair test fails with a recorded reason. The rule is frozen before the draw.

How the cases are drawn

  1. A public OSF record fixes the ledger, the adaptation rule and the selection script by their SHA-256 digests.
  2. The seed is the drand beacon value of a round at least 24 hours after publication. Nobody can know it in advance, and anyone can check it.
  3. The script orders the cases by a hash of the seed and each case id.
  4. A cap limits how many cases one attack scenario may contribute, because many cases repeat a few attacks.
  5. Injection and unsafe-action places are shared out in proportion to the two pools.
  6. Cases go through the adaptation rule in that order. A passing case joins the sample. A failing case is reported with its reason, and the next case is tried.

The pilot draw runs first, with its own record and seed. The main draw of 299 uses a second record and a new seed, without the pilot and development cases. After the main draw, no case is replaced.
