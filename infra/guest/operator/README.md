# tbound-op: operator dispatcher for the TBound guest

Spec: `DESIGN.md` (same directory). Tests: `TESTS.md` (generated by `run-tests.sh`).

Local regressions: `bash infra/guest/operator/test-local.sh` from the checkout on Linux, as a non-root user. They extract only the fixture functions into a temporary-directory harness, substitute the current user's uid/gid, and stub service/mount/reporting commands; they never execute the dispatcher preamble or contact a guest. The historical guest results in `TESTS.md` do not verify later changes.

After Z1' the automation (tboundadmin) has no unrestricted root. Its only sudo rule is

    tboundadmin ALL=(root) NOPASSWD: /opt/tbound/operator/tbound-op      (/etc/sudoers.d/50-tbound-op, 0440)
    Defaults!/opt/tbound/operator/tbound-op env_reset,!setenv

Call it as `sudo -n /opt/tbound/operator/tbound-op <verb> [args]`. There is no verb that takes a path or a free-form command.

## Rules that hold for every verb

- Arguments: every argument must match `^[A-Za-z0-9._:,=-]{1,160}$` and must not contain `..`; then per verb: `NAME = smoke|g1|rp|dr|pilot`, `SHA = (sha256:)?<64 hex>`, `RUNID = [A-Za-z0-9._-]{8,128}` with `/var/lib/tbound/audit/<RUNID>-session-audit.jsonl` present, `RID = (smoke|g1|rp|dr)-req-<yyyymmdd>T<hhmmss>Z`, generated by the dispatcher only. Wrong verb, name, argument count or character: exit 2.
- `/var/tmp/tbound-op` is an export destination only: nothing under it is ever read back. Every verb first requires it (and each `<NAME>/` or `_/` below it, when used) to be a real directory `root:tboundadmin 0750`; a missing one is created root-owned (`mkdir 0700`, then chown/chmod), anything else (wrong owner or mode, symlink, made by tboundadmin) makes the verb fail until the owner removes it.
- One verb at a time (`flock -w 5 /run/tbound-op.lock`); `status`, `diag`, `collect` take no lock. A running `client-run` keeps the lock until the client returns (up to about 20 minutes), so no other mutating verb runs meanwhile.
- Staged inputs are read from `/home/tboundadmin/stage-<NAME>/<fixed file name>` only: opened `O_NOFOLLOW` (home, stage dir, file; regular file owned by tboundadmin; size cap), copied into a root-only tmpfs work dir (`/run/tbound-op/w.*`), hashed and verified there, installed from that copy. A swap after the copy cannot change what is installed (race test in `TESTS.md` section 5).
- Before anything runs: `sha256(/etc/tbound/pi-host-profile.pub) == ADMIN_PUB_DIGEST`; before verification: `/usr/local/bin/tbound == TBOUND_DIGEST` and `/usr/local/bin/tbound-profile == TBP_DIGEST`.
- Installs are atomic (`.new` + `mv -f`); an already-equal file is a no-op success. Backups under `/root/ga/prev/<NAME>/<file>` are written once and never replaced.
- State per NAME: `config -> reg -> prof -> started` (`started` is set by `svc start` / `adopt`). `client-run` is allowed once per NAME (`<NAME>.once`), also after a rollback.
- `seed-live` and `reg-measure` check the live mount/root and refuse symlinks anywhere in the existing live tree before fixture setup. Existing root/fence/src/out directories must already have the required uid/gid and modes; the dispatcher never repairs their metadata. Missing directories use `mkdir`; all writes below the live root run as uid 995/gid 986 with the service privilege restrictions. A malformed existing tree needs owner inspection.

## Verbs

Staged file names are per NAME directory `stage-<NAME>`.

| verb | staged files | what it verifies, then does |
| --- | --- | --- |
| `status [NAME]` | | anchor, tool digests, service/socket state, installed hashes, which NAME's state matches the installed config, state files, client status, log tail |
| `diag l2\|mounts\|census-live\|podman-ps\|podman-ps-noreap\|nft-sink\|probe-capabilities\|image-probe\|live-listing\|netsink-journal-size` | | fixed read-only wrappers (podman as uid 995 with the service environment); output also in `_/diag-<kind>.txt` |
| `collect l4\|evidence-out\|requests\|catalog\|audit RUNID` | | allow-listed copies into `_/` (audit needs the session audit file of RUNID; `l4` also writes `l4.txt`) |
| `cfg-install NAME SHA` | `serve-pi-service.json` | service stopped; no spent admission; the copy hashes to SHA and equals the shipped template of NAME (pinned) byte for byte after substituting the two podman-config digests (= sha256 of the installed files), for `dr` also a NEW admission id (not in any template or earlier dr), for `pilot` the corpus digest of the installed manifest; backup; install 0644; state `config` |
| `reg-measure NAME` | | state `config` with the installed config; service stopped; `/root/ga/reg-<NAME>` absent; creates the parent cgroup (removed by a trap), runs `managed-root-measure` with the fixed flags, checks runner == TBOUND_DIGEST, uid 995, `service_config_digest` == installed config, account digests == files; result in `/root/ga/reg-<NAME>/` and `/var/tmp/tbound-op/<NAME>/managed-live-root.unsigned.json` |
| `reg-install NAME SHA_JSON SHA_SIG` | `managed-live-root.json`, `managed-live-root.ed25519` | `managed-root-verify` under the anchor with `--runner-digest TBOUND_DIGEST`; registration binds the installed config digest and the current account digests; backup; install; re-verify; state `reg` (records REGDIGEST) |
| `prof-install NAME SHA_PROFILE SHA_SIG SHA_TEMPLATE [SHA_PRODTEMPLATE]` | `pi-host-profile.json`, `pi-host-profile.ed25519`, `d09-cell.json` (for `dr`: `d09-cell.route-probe.json` = installed probe template, plus `d09-cell.json` = production template, SHA_PRODTEMPLATE required for dr only) | `tbound-profile verify --runtime-bundle-digest BUNDLE_DIGEST`; template BASE_TD == pin, TD == profile `ContainmentProfileDigest`, template names the recorded REGDIGEST and IMGDIGEST, profile source == SRC_DIGEST, bundle == BUNDLE_DIGEST, `route_probe` only in the dr probe template; dr production == probe minus `route_probe`; backup; install; re-verify the installed chain; archive to `/root/ga/<NAME>/` (RG-7 names) with `archive.sha256`; state `prof` |
| `adopt smoke` | | the same chain verification on the installed smoke files, no install; archive to `/root/ga/smoke/`; state `started` if service and socket are active, else `prof` |
| `rollback NAME cfg\|reg\|prof\|all` | | service stopped; every needed backup must exist (else nothing changes); restore; re-verify signatures; the NAME's state is cleared (run `adopt` or the cycle again) |
| `manifest-install SHA CORPUS_DIGEST` | `stage-pilot/manifest.json` | `corpus-digest` (pilot quotas, fixed flags) of the copy == CORPUS_DIGEST; service stopped; install `/etc/tbound/corpus/manifest.json` 0644; re-verify; records the digest |
| `svc start\|stop` | | stop: service and socket. start: some NAME with state >= `prof` matches the installed config, every installed file equals the recorded hash, full chain re-verified; starts socket, then service; journal in `<NAME>/svc-start-journal.txt`; state `started`. The socket is never left stopped by a failing start |
| `seed-live smoke\|g1` | | creates the live root `/var/lib/tbound/live/root` (995:986 0700) and its fence directory `lost+found` (995:986 0755) beneath the mount root if missing; smoke: contents exactly `SMOKE-README.txt` (0644 995:986), no-op if already so (any service state); g1: service stopped, `src/release.txt`, `out/`; listing (image root, live root, census) to `<NAME>/live-listing.txt` |
| `client-run smoke\|g1\|rp\|dr` | | NAME's state `started` and its config installed, service+socket active, chain re-verified, live root matches the fixture, no earlier client-run for NAME; task id / bash flag from a fixed table cross-checked against the installed config; prompt from the config; generates the RID; runs the client (uid 994 / gid 985, no-new-privs) detached; response `/root/ga/out/{smoke-response,response,probe-response,dr-response}.txt` mirrored to `<NAME>/`; authoritative status in `/root/ga/state/<NAME>.client-status` (root-only, written by the detached client; `status NAME` reads only that), export copy in `<NAME>/client-run.status` |
| `negative n2\|n5\|n6\|n7` | | fixed command lines of Part L5, result PASS/FAIL in `<dir>/negative-<k>.txt`. n2, n5 any time; n6, n7 only after the smoke client-run (smoke config installed); n7 once |
| `abandon RID` / `abandon RID --confirm TOKEN` | | RID must be one the dispatcher generated and appear in `serve-pi-requests.jsonl`. First call prints the L4 fact list and `TOKEN` (first 12 hex of its sha256); second call recomputes, needs the same token, then stops service+socket, runs `tbound abandon-unknown` with a fixed reason, starts the socket |
| `stage-ga tbound-profile\|procoracle-test\|cell-entrypoint-test\|run-json SHA` | `stage-ga/tbound-profile`, `procoracle.test`, `tbound-cell-entrypoint.test`, `run.json` | compares with the pin (TBP_DIGEST, TEST_*) or, for run.json, with the file generated from pins.env; installs 0500 (run.json 0444) into `/root/ga/` |
| `guest-evidence capability\|netsink\|landlock-connect\|procoracle\|provider-exchange\|route-bash-view RUNID\|route-direct-runtime RUNID` | | hard-wired flags of the evidence table; needs `/root/ga/tbound-profile` == TBP_DIGEST, `/root/ga/run.json` == generated from pins, test binaries == pins, the archived `/root/ga/<NAME>/` files (key == ADMIN_PUB_DIGEST); refuses an existing output; result in `_/evidence-<name>.json` |
| `netsink-rotate` | | stops `tbound-netsink`, renames the journal with a UTC suffix, starts it, requires it active |

## RG cycle for g1 (every step from the automation's side)

Owner machine first: fill `serve-pi-service.g1.json` (the two podman-config digests, `sha256sum` of the installed files), sign nothing yet.

    GSSH 'install -d -m 0700 ~/stage-g1' ; GSSH 'cat > ~/stage-g1/serve-pi-service.json' < $H/g1/serve-pi-service.json
    OP='sudo -n /opt/tbound/operator/tbound-op'
    GSSH "$OP svc stop"
    GSSH "$OP cfg-install g1 <sha256 of the staged config>"
    GSSH "$OP reg-measure g1"                      # then fetch /var/tmp/tbound-op/g1/managed-live-root.unsigned.json (readable by tboundadmin)
    # owner machine: S3g signs it (RG-4) -> managed-live-root.json + .ed25519; stage both in ~/stage-g1
    GSSH "$OP reg-install g1 <sha json> <sha sig>"
    # owner machine: template with REGDIGEST-g1, profile S4g (RG-6); stage pi-host-profile.json, pi-host-profile.ed25519, d09-cell.json
    GSSH "$OP prof-install g1 <sha profile> <sha sig> <sha template>"
    GSSH "$OP seed-live g1"
    GSSH "$OP svc start"
    GSSH "$OP diag l2"                             # L2
    GSSH "$OP client-run g1"                       # detached; poll with: $OP status g1
    GSSH "$OP collect l4"                          # after the client returned; files in /var/tmp/tbound-op/_/
    GSSH "$OP stage-ga tbound-profile <sha>" ; GSSH "$OP stage-ga run-json <sha>"       # once
    GSSH "$OP guest-evidence provider-exchange"
    GSSH "$OP svc stop"

rp and dr follow the same pattern (`dr`: the config has a new admission id; `prof-install dr` takes both templates). Before the g1 cycle the smoke must be settled: N7 and `abandon` first (they need the smoke config), then `svc stop`.
Rollback of a failed cycle: `svc stop`, `rollback <NAME> all` (restores the `prev/<NAME>` set, i.e. the previous NAME's files), then `adopt smoke` or the previous cycle's verbs to rebuild the state.

## Owner-only (not verbs)

Account, sudo and ssh changes; binary and mount reinstalls (runner swap, podman/crun/git upgrades); provider key entry (no `provider-key` verb); N1 concurrency test; Spike B probes (no `spikeb` verb); recovery from half-applied cycles; anything that needs the owner signing key; editing `pins.env` (e.g. adding TEST_PROCORACLE / TEST_ENTRYPOINT, or a new freeze); any arbitrary-command escape (none by design).

## Known limits

- `reg-measure NAME` refuses when `/root/ga/reg-<NAME>` exists (a smoke measurement from the test run is there); leftovers of a failed cycle need an owner `rm`.
- Verified on the real guest only for the smoke chain (identical re-install paths, tamper and signature refusals, measure == installed registration). The g1/rp/dr/pilot installs run the same code but need owner signatures; `dr`/`pilot` config rules are unit-tested against the real templates on the owner machine (`cfgcheck` cases in the build log) and not installed.
- Logging goes to `/var/log/tbound-op.log` (adm can read); journald is persistent (`/var/log/journal`), and tboundadmin is in group adm.
